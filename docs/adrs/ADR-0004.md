# ADR-0004: Redis Lock plus Database Versioning

| Field | Value |
|---|---|
| **Status** | Accepted |
| **Date** | October 2026 |

## Context
In a multi-replica distributed deployment, concurrent payment workers across different service instances may attempt to process transactions involving the same customer accounts simultaneously. Relying exclusively on database-level locking causes severe contention on hot accounts, long queue waits, and connection pool exhaustion. Conversely, relying exclusively on a single-node Redis lock is unsafe: process pauses (GC pauses, network delays) can outlast the lock TTL, allowing a secondary worker to acquire the lock and cause split-brain balance updates.

## Decision
Adopt a defense-in-depth hybrid concurrency control model:
1. **Redis Distributed Lock (Operational Guard):** Sits at the entrance of processing to arbitrate mutual exclusion across instances, reducing database contention and preventing duplicate in-flight work.
   - Acquired via `SET lock:account:{id} <token> NX PX <ttl>`.
   - Token is cryptographically unique per attempt.
   - Released strictly via an atomic Lua script that verifies token ownership before deletion.
   - Protected by an automatic watchdog background renewal goroutine running at roughly `TTL / 3`.
   - Multi-account transfers acquire locks deterministically in ascending UUID order to eliminate distributed deadlocks.
2. **PostgreSQL Optimistic Versioning (Correctness Arbiter):** The ultimate source of truth. Every account balance mutation enforces `UPDATE accounts SET balance = ..., version = version + 1 WHERE id = $1 AND version = $expected`. Even if a Redis lock lapses mid-flight, a stale writer fails atomically without corrupting data.
3. **Graceful Degradation:** If Redis becomes unavailable, lock acquisition fails fast and execution seamlessly falls back to PostgreSQL row-level locking (`FOR UPDATE`). Throughput temporarily drops under high contention, but mathematical consistency and money invariants remain uncompromised.

## Consequences
- **Positive:** Maximum throughput under multi-replica operation by buffering contention before it reaches PostgreSQL.
- **Positive:** Uncompromised data consistency even across network partitions or GC hiccups.
- **Trade-off:** Two distinct locking mechanisms to test and monitor.

## Alternatives Considered
- **Database-Only Locking:** Simpler, but database connection pools saturate rapidly under multi-instance load spikes.
- **Redis-Only Mutual Exclusion:** Unsafe for financial ledgers due to TTL expiry and split-brain risks.
- **Redlock Multi-Node Algorithm:** Complex coordination across multiple independent Redis clusters with debated safety under asynchronous clock drift; unnecessary given PostgreSQL fencing.
