# ADR-0006: Bounded Worker Pool with Backpressure

| Field | Value |
|---|---|
| **Status** | Accepted |
| **Date** | October 2026 |

## Context
Spawning a fresh goroutine for every incoming HTTP payment request is computationally cheap in Go, but completely unbounded. Under sudden traffic surges or upstream slowdowns, unbounded concurrency exhausts database connections, overflows heap memory, degrades cache locality, and causes cascading outages.

## Decision
Implement a fixed-capacity worker pool of $N$ goroutines consuming from a buffered Go channel (`chan Job`) with a bounded queue capacity ($Q$).

Key mechanisms:
1. **Backpressure:** If the buffered channel is saturated, the API immediately rejects the request with HTTP `429 Too Many Requests` and a `Retry-After` response header, preventing runaway queuing.
2. **Crash Resilience (Reaper):** In-memory buffered jobs are volatile and lost if an instance restarts or crashes. The PostgreSQL database serves as the durable backing store. A background **Reaper** process runs periodically to detect orphaned payments stuck in `PENDING` or `PROCESSING` past an expiration threshold (`REAPER_STALE_AFTER`) and safely re-enqueues them.
3. **Panic Isolation:** Every worker wraps its job execution in a `recover()` block to log panics, prevent worker deaths, and record a transient failure status for subsequent retry.

## Consequences
- **Positive:** Bounded, deterministic CPU and memory consumption regardless of incoming request volume.
- **Positive:** Fast ingestion latency with backpressure feedback to upstream callers.
- **Trade-off:** In-flight in-memory jobs rely on periodic reconciliation by the Reaper in the event of an abrupt host termination.

## Alternatives Considered
- **Unbounded Goroutines (`go handler()` per request):** Rejected due to risk of OOM and connection exhaustion.
- **Immediate Enqueue to External Broker Only:** Adds extra external hop on the critical HTTP ingress path.
