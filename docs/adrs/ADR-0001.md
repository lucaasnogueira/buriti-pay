# ADR-0001: Asynchronous processing with 202 Accepted

| Field | Value |
|---|---|
| **Status** | Accepted |
| **Date** | October 2026 |

## Context
Doing distributed locking, database transactions, and event publishing synchronously inside the HTTP request loop ties client latency directly to the slowest dependency. Under load spikes, this leads to connection pool exhaustion, timeout cascades, and degraded client experience.

## Decision
`POST /payments` persists the payment as `PENDING`, enqueues a job into an in-memory bounded channel, and returns `202 Accepted` immediately with the payment ID. Processing occurs asynchronously via a worker pool. Clients poll `GET /payments/{id}` or consume asynchronous confirmation events.

## Consequences
- **Positive:** Low and predictable API ingest latency (< 50ms p99).
- **Positive:** System handles traffic bursts via bounded channel backpressure (`429 Too Many Requests`).
- **Trade-off:** Clients must handle eventual results. Requires a background reconciliation mechanism (Reaper) to re-enqueue lost in-memory jobs in the event of an abrupt process crash.

## Alternatives Considered
- **Synchronous processing:** Simpler to implement, but leaks latency and risks cascading failures during downstream contention.
- **Message broker as intake queue:** Enqueue directly to RabbitMQ from API. Adds extra network hop on the critical ingress path and external dependency for ingestion.
