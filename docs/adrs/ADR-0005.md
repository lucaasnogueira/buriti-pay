# ADR-0005: Transactional Outbox Pattern

| Field | Value |
|---|---|
| **Status** | Accepted |
| **Date** | October 2026 |

## Context
Confirming a payment and publishing an event to RabbitMQ represent dual writes across two distinct distributed systems (PostgreSQL and RabbitMQ). Publishing directly after committing can lose events if the application crashes before the broker call. Conversely, publishing before committing risks phantom events if the database transaction rolls back.

## Decision
Adopt the **Transactional Outbox Pattern**:
1. Every state mutation (`payment.confirmed` or `payment.failed`) records an `OutboxEvent` row inside the identical PostgreSQL database transaction as the account balance updates.
2. An asynchronous background **Outbox Relay** process polls for unpublished rows (`WHERE published_at IS NULL`) and publishes them to the RabbitMQ `payments.events` topic exchange with AMQP **Publisher Confirms** enabled.
3. Upon receiving positive broker confirmation, the relay marks `published_at = now()` atomically.
4. Consumers implement manual message acknowledgments (`ack`/`nack`), bounded prefetch, retry queues, and Dead-Letter Exchanges (`payments.dlx`), with client-side deduplication by `event_id` ensuring safety under at-least-once delivery.

## Consequences
- **Positive:** Zero lost events and zero phantom events across broker downtime or application crashes.
- **Positive:** Financial state updates remain decoupled from message broker network latency.
- **Trade-off:** Introduces a small relay polling latency and delivers messages *at-least-once*, requiring downstream consumers to be strictly idempotent.

## Alternatives Considered
- **Direct Publish Post-Commit:** Prone to silent event loss upon process crash.
- **Two-Phase Commit (2PC / XA):** Heavy coordination, poor cloud tooling support, and severe latency penalty.
