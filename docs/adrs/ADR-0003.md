# ADR-0003: Idempotency Keys

| Field | Value |
|---|---|
| **Status** | Accepted |
| **Date** | October 2026 |

## Context
Clients interacting with payment APIs often experience network timeouts, transient disconnections, and automated retry loops. Without strict idempotency controls, repeated requests risk executing multiple debits for the same intended transaction (double-spending / duplicate charges).

## Decision
Require an `Idempotency-Key` HTTP header on all `POST /payments` requests. Enforce uniqueness through a PostgreSQL database constraint on `payments.idempotency_key`.

Handling rules:
1. **Identical Key and Payload:** Return the originally registered payment immediately without re-processing.
2. **Identical Key but Different Payload:** Reject the request with HTTP `409 Conflict`.
3. **Consumer Event De-duplication:** Downstream message consumers de-duplicate events based on `event_id`.

## Consequences
- **Positive:** Complete end-to-end duplicate charge prevention.
- **Positive:** Database uniqueness constraint acts as the unshakeable arbiter under high concurrency.
- **Trade-off:** Clients must generate and persist unique keys (typically client-generated UUIDs). Keys accumulate over time and will require retention cleanup strategies in production.

## Alternatives Considered
- **Redis-only Deduplication:** Fast, but data can be lost upon Redis eviction or restarts, breaking financial consistency guarantees.
- **Natural-key Matching:** Identifying transactions based on `(from_account, to_account, amount, timestamp)` is ambiguous and rejects legitimate back-to-back transfers.
